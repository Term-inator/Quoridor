# Pygame 交互原型回交

Status: awaiting hands-on verdict

## 原型回答的问题

在真实 Pygame 窗口中比较三个左棋盘/右侧栏方案，确认：

1. 棋盘与侧栏比例；
2. 8×8 墙锚点吸附；
3. 合法/非法动作反馈；
4. 960×640、1280×800 和大窗口下的可读性。

## 原型位置与边界

- 入口：`pygame_ui_prototype.py`
- 运行和体验路径：`README.md`
- 正式规则边界：直接维护不可变 `Position`，只提交 `MovePawn` / `PlaceWall`。
- 内存状态：不存档、不跨进程保存。
- 明确未做：开始菜单、完整模式矩阵、智能体播放、胜负流程、生产入口、正式测试和错误处理。

## 已验证的工程行为

- 三个结构不同的方案可以在同一局面中即时切换，切换不会重置规则状态。
- 初始合法棋子目标来自 `Position.legal_actions()`，点击后由 `Position.play()` 推进。
- 横墙和竖墙共享 8×8 锚点吸附；预览是否合法仍由规则核心决定。
- 非法墙点击捕获结构化 `IllegalActionReason`，显示中文原因且不推进手数。
- 所有方案在 960×640 下仍显示棋盘坐标、操作按钮、反馈和压缩后的完整交互状态。
- 原型可在 headless SDL 下渲染九张尺寸截图；源文件通过 Ruff 检查。
- 交互 smoke 覆盖合法移动、合法放墙、同锚点非法放墙和保留状态的方案切换；非法点击后仍为第 2 手且仍由 `player_0` 行动。
- 正式项目回归验证为 `31 passed`；PettingZoo 自带检查仍输出仓库原有的两条 observation 建议警告。

## 截图检查的初步观察

- A 在最小窗口中保留约 512 px 棋盘，单格约 44 px，落子最舒展，但侧栏只能采用紧凑状态摘要。
- B 在最小窗口中使用约 461 px 棋盘，换取更宽的反馈和状态区域；操作反馈最靠近模式按钮。
- C 在最小窗口中使用约 420 px 棋盘，坐标和目标仍可辨认，但明显把视觉主导权交给规则状态，适合调试而不一定适合纯人类对局。
- 最小尺寸必须使用紧凑信息布局；直接沿用默认尺寸的纵向卡片会发生状态裁切，这一问题已在原型中显式处理。

这些是渲染检查，不替代鼠标手感和真人阅读判断。
